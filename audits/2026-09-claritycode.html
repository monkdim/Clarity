Section 2

Gaps by tier

Immediate

Nobody can install Clarity.
GET /repos/monkdim/Clarity/releases/latest  ->  tag V1.0.0, "assets": []
The README's "Try Clarity in 60 seconds" pipes install.sh, which downloads clarity-linux-x64.tar.gz from the latest release and gets a 404. Formula/clarity.rb has four sha256 "PLACEHOLDER" and lowercase v#{version} URLs against a capital-V tag. registry/Dockerfile bootstraps the same way and cannot build. CI's "bootstrap from latest release" step fails every run and silently falls through to Python (continue-on-error). All four were reported in July and none has changed. Fix: tag v1.0.1, let build.yml attach the five archives, fill the Formula hashes, delete releases/.
The single binary cannot import its own standard library.
$ clarity run u.clarity        # u.clarity: from "collections.clarity" import Set
RuntimeError: Cannot find module: collections.clarity (line 1)
Imports resolve to files on disk. Without a repo checkout beside the program, "batteries included" and "ships as a single binary" are true of the toolchain and false of every library. Fix: embed the transpiled stdlib in the binary and resolve from "x.clarity" against it before the filesystem.
The self-hosted compiler cannot rebuild the toolchain on its own.
$ ./clarity transpile --bundle -o /tmp/selfdist      # 138 modules emitted
$ bun /tmp/selfdist/clarity-entry.js version
error: Cannot find module './kyan_desktop.js' from '/tmp/selfdist/cli.js'
transpile.clarity carries a hard-coded STDLIB_FILES of 138 names; native/transpile.py carries its own list of 150. Twelve modules the CLI statically imports (kyan_desktop, host, theme_kyan, pty, terminal_emulator, claude, the fonts) are only in the Python list. The self-hosting CI job passes because stage 2 writes over the stage 1 directory, so the Python-emitted files fill the holes and the "fixpoint" compares two hybrids. Eight more modules, the entire RE toolkit (bytes, bits, binformat, capstone, hook, procmem, sha256, benchmark), are in neither list. Fix: one bundler, driven by a glob of stdlib/ plus the import graph, and a CI stage that bundles into an empty directory.

Huge

clarity cc compiles one file.
It does not resolve imports, so native programs inline what they use; every RE example does. Track B's ergonomics and the "any Clarity program compiles" goal both wait on import flattening. Thirteen constructs still raise native compile: unsupported (indirect calls, spread, some unary and binary operators, open-ended ranges, break or continue inside a try with a finally, and whole statement and expression kinds). Enums and generators are open.
The bytecode VM ignores imports.
$ clarity run imp.clarity --fast
RuntimeError: Undefined variable: Set
Reported in July; still true. --fast is unusable for any program with an import, which is any program using the library.
29 modules, 10,274 lines, have no test that imports them.
Among them cli.clarity (1,545 lines, the entry point), package.clarity, install.clarity, net.clarity, path.clarity, datetime.clarity, semver.clarity, runtime_spec.clarity. Ten of them (3,087 lines: benchmark, channel, collections, crypto, db, http, mutex, registry, runtime, worker) are imported by nothing at all, tests included, and most are headline features in the V1.0.0 release notes.
native/runtime.js cannot be regenerated.
GAPS.md records it: gen-runtime produces a large diff, and regenerating would revert fixes that exist only in the committed file. Every builtin change is a hand edit in two places. This is the language's runtime, and its spec is decorative.
The playground runs a second interpreter.
playground/index.html line 322: "Minimal Clarity interpreter in JS for the playground", hand-written, last touched 14 February. It cannot agree with the real language for long. The browser build in web/ already proves the real runtime runs in a page.

Medium

fmt still drops comments.
-- a comment that must survive      (input)
let s = "a\nb"                      (output: the comment is gone)
The lexer discards comments and the formatter is AST-only. fmt --write on the stdlib would delete every comment in it. The escape bug is fixed; this one is not.
args() under clarity run includes the command and the script.
$ clarity run a.clarity one two    ->    ["run", "a.clarity", "one", "two"]
Native binaries get it right. Known in ROADMAP.md; still open. Every script that reads arguments differs between the two engines.
The transpiler and formatter emit TODO comments instead of failing.
transpile.clarity lines 231 and 523 write /* TODO: <node> */ into output for unknown AST nodes; formatter.clarity line 87 writes -- TODO:. A new syntax node silently becomes a comment in generated JavaScript.
The shipped bundle and the deployed site are two months old.
web/kyanos.bundle.js (July 12) is tracked in git and copied by pages.yml without rebuilding; its sources changed September 5. docs/*.html date from July 11. The REPL banner says Clarity Shell v0.5 in a 1.0 binary.
The VS Code extension cannot be packaged as written.
vscode-languageclient is a runtime import declared under devDependencies; the extension calls clarity fmt --stdout, a flag the CLI does not have (it prints to stdout by default and takes --write); no icon is declared.
Bitwise operators are 32-bit signed.
& | ^ << >> truncate to int32 in the interpreter, the VM and native. bits.clarity works around it to 2^53. Making the operators 64-bit is a semantics change across three engines and is the right change for an RE toolkit.
Optional features are startup dependencies.
Both transpilers hoist function-scoped from ... import to static top-level imports, so cli.js imports host.js (SDL2) and kyan_desktop.js whether or not desktop is ever invoked. It is why the self-hosted bundle fails at version, not at desktop.

Low

  • releases/ holds three Mach-O binaries, about 180 MB, tracked in git, referenced by nothing, named unlike anything build.yml produces.
  • test_smoke.clarity is in both bundle lists; a test module ships inside the binary.
  • website_gen.clarity bakes in clarityos.dev, a domain the project does not own; test_polish.clarity asserts it.
  • build.yml only runs on tags and no tag has been pushed since February, so no artifact of the current code has ever been built by CI.
  • README numbers: "~2,750 assertions across 50 test files" (64 files, about 3,500 assert calls), "56 opcodes" (57), "eight tours" (17 examples), "~58,000 lines of Clarity" (68,004).
Section 3

What is strong

  • The suite is real and it is green. 64 files, three targets, every commit. It caught nothing in this audit because nothing it covers is broken; what is broken is outside it.
  • The native compiler is the best-engineered thing in the tree. Twenty stages, each landed with a test that compiles the generated C and diffs it against the interpreter. A conservative GC with a measured cost model. A freestanding profile that the kernel runs. This is the language's future and it is being built carefully.
  • Track B is not a slide. Signature scanning, live-process read and write, function hooking, a binary-format DSL and a Capstone binding all compile to standalone binaries and all have runnable examples. The pure-Clarity-over-primitives thesis is demonstrated, not asserted.
  • Self-hosting is nearly true. Lexer, parser, interpreter, VM, checker, linter, formatter, debugger, profiler, docgen, LSP, package manager, transpiler: all Clarity. The one gap is the bundle list, and it is a list.
  • Errors point at the column. Parse errors show the source line and a caret; the type checker flags arity and undefined names with no false positives across the stdlib.
  • The July audit was acted on. REPL execution, profile and debug, map iteration, fmt escapes, cwd-independent lsp: fixed. What remains open is listed above with the evidence that it is still open.
Section 4

What is holding us back

  1. Distribution has been broken since February. Every path to a user (install script, Homebrew, Docker, CI bootstrap) fails on the same missing assets. One correctly-cased release with binaries attached fixes all four. Nothing else on this page matters to a stranger until this does.
  2. Two hand-maintained lists decide what the language is. The bundle lists are the real definition of "the standard library", they disagree with each other and with the directory, and the RE toolkit the roadmap is proudest of is in neither.
  3. Three engines, one semantics, no parity suite. Interpreter, bytecode VM and native disagree on imports and on args(). The native path has a diff-against-interpreter harness; the VM has nothing equivalent. Parity should be a test, not a hope.
  4. The runtime's source of truth is a generated file that cannot be generated. Until runtime_spec and runtime.js are reconciled, every builtin is two edits and a prayer.
  5. Stale artifacts are tracked in git and deployed as-is. The web bundle, the docs, the playground's private interpreter and the release binaries all describe an older language.

Section 6

Code challenged

  • A list of filenames is not a module system. Two lists, two languages, both wrong. The transpiler already resolves imports to build the graph; the bundle should be that graph's closure from cli.clarity plus everything under stdlib/ a user could import.
  • Hoisting scoped imports to static ones changes the program's meaning. A lazy import inside if command == "desktop" becomes a hard dependency at load. Either the transpiler emits a dynamic import() for scoped imports, or the CLI should not pretend they are optional.
  • Emitting /* TODO */ into generated code is a silent failure. An unknown node should stop the build with a line number. The same applies to the formatter's -- TODO:.
  • "Assertions" is counted loosely. The README's figure is a grep of assert calls; test files also use ok(...). Either count both consistently or report files and pass counts, which the runner already prints.
  • The self-hosting job proves reproducibility, not self-sufficiency. It should bundle into an empty directory, compile, and run the suite from that. Today it cannot, and the job does not know.
  • host_supported() answers the wrong question. It reports the platform; the failure is a missing library. Check for SDL2 and print the sentence that already exists in the code.
  • Generated files in git without a check. native/runtime.js, web/kyanos.bundle.js, and now REPO_INDEX.md. The index ships with --check so CI can fail when it is stale; the other two should get the same.

Section 8

Not gaps, but assets for the goal

  • One compiler serves both products. clarity cc with --freestanding is how a Clarity program reaches the kernel. Every Track A stage is also a KyanOS userspace capability.
  • The RE toolkit is a wedge into games. Scanning, live memory, hooking and disassembly are the primitives a mod loader and a trainer are built from; they exist and they compile natively.
  • The LSP and the VS Code extension are substantial. Hover types and go-to-definition work; the extension is a real client. Packaging is the only thing between it and a marketplace listing.
  • The browser runtime exists. web/runtime_browser.js stubs Bun and keeps all builtins; it is the basis for a playground that runs the real language.
  • The test runner prints exactly the numbers the README should quote. 64 passed, 0 failed / 64 total, per-module counts included. The documentation only has to copy them.
Section 9

What needs doing, in order

  1. Publish v1.0.1 with the five archives attached; fill the Formula hashes; remove releases/. This unbreaks install, Homebrew, Docker and the CI bootstrap in one action.
  2. Replace both bundle lists with one graph-driven bundler; make the self-hosting job bundle into an empty directory and run the suite from it; add the RE toolkit and the Kyan modules by construction.
  3. Embed the transpiled stdlib in the binary so from "collections.clarity" works anywhere.
  4. Make the VM resolve imports, and add an interpreter-versus-VM parity suite modeled on the native one. Fix args().
  5. Reconcile runtime_spec with runtime.js so gen-runtime is safe, and gate it in CI.
  6. Give the 29 untested modules tests or a decision; start with cli.clarity and package.clarity.
  7. Import flattening in clarity cc; then enums and generators; then 64-bit bitwise operators.
  8. Rebuild the web bundle in Pages, replace the playground interpreter with the real runtime, regenerate the docs, fix the extension's packaging, and let the README quote the runner and the index.
