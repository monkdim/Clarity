Section 2

Gaps by tier

Immediate means a person following the README hits it today. Huge means it blocks the goal (a Mac-style OS on Apple hardware that can run PC games). Medium is real and bounded. Low is hygiene.

Immediate

clarity os build fails on a clean tree.
  zig build in kernel ...
  zig build in runtime/freestanding ...
  expected runtime artifact missing at runtime/freestanding/zig-out/bin/clarity-runtime
os build exit=1
The freestanding runtime is QuickJS-based and QuickJS is never vendored; runtime/freestanding/build.zig prints a warning and installs nothing. The kernel the gates boot does not use this runtime at all; it embeds clarity-init (Zig) and clarity-demo (C from clarity cc). Fix: make os build produce the ISO the gate boots, with GRUB via mkiso's grub-mkrescue path, and drop the QuickJS runtime from the pipeline. It is a separate, non-working pipeline being advertised as the developer workflow.
The README's boot path does not match the gate.
README: "Multiboot2 → ELF loader → ring switch → SYSCALL → page faults → fork/exec/wait/kill → framebuffer → init → tmpfs/devfs/procfs → desktop session → login." What the gate proves ends at two processes and ClarityOS: userspace complete. Page faults are reported and the machine halts (vmm.handle_page_fault has no caller). devfs and procfs are compile-only. No desktop session or login runs on the kernel. Fix: state the gate's markers as the boot path.
"The userspace is written in Clarity" is not true on the kernel.
On both kernels init is Zig (kernel/user/init.zig, init_aarch64.zig). The Clarity init, init_app, vfs, scheduler, process_model, procfs, compositor, desktop_session and every app are imported only by tests; none has ever run on the kernel. syscall.clarity's claritos backend throws "not yet wired"; display_server.framebuffer_from_mmap throws "not implemented yet". Fix: say "a userspace written in Clarity exists and runs hosted; on the kernel, one Clarity program runs".
HVF cannot run either kernel on Apple Silicon.
qemu-system-aarch64: HVF does not support GICv2 emulation
The aarch64 kernel speaks GICv2 only, and HVF refuses it. The launcher (qemu_macos.clarity) only ever starts qemu-system-x86_64, which HVF cannot accelerate on an ARM host. The README's "targets QEMU first on macOS (HVF)" is not achievable on the hardware the project is for. Fix: GICv3 driver (roadmap item, already recorded), and a launcher that picks the aarch64 kernel on arm64 hosts.
x86_64 system calls dereference raw user pointers.
// Note: the buffer is a raw user pointer and is not validated. Nothing
// here checks that the range is mapped, user-owned, or even canonical, so
// a bad pointer faults in the kernel.        (syscall/dispatch.zig, sys_write)
sys_read, sys_write and sys_open all do this. The aarch64 side translates every user pointer through the process's own tables and enables PAN; the x86 side has none of it. A bad pointer from a program is a kernel fault, not an EFAULT. Fix: port the aarch64 translate-for-read / translate-for-write layer and enable SMAP.

Huge

No scheduler or process table on aarch64.
Threads switch, programs run one after another from a fixed boot order. There is no exec, so nothing can start a program; read(2) cannot block, so it spins and gives up (now two minutes by default, from the kernel command line). Every session feature waits on this.
GICv3, then AIC.
Native speed on Apple hardware needs GICv3 under HVF; real hardware needs m1n1 and Apple's AIC, not a GIC at all. Both are known and neither is started.
Preemption stops at the kernel's door.
System calls run with interrupts on (so devices are serviced), but a time slice that expires inside one is ignored: trap.zig counts syscall_depth and aarch64_irq skips the scheduling decision. A program in a long call cannot be preempted. This is honest and documented, and it is still a gap.

Medium

Every process shares one descriptor table.
vfs.install_current_table_resolver is never called, so current_table() always returns fallback_table. Two processes opening files would see each other's descriptors. File records are freed only on close; nothing closes them on exit.
The kernel heap is written to once and freed almost never.
heap.free has two callers in the whole kernel (tmpfs growth and vfs.close). Everything else leaks by design. Fine for a boot that ends, not for a session.
Stubs that look like drivers.
drivers/ahci.zig and drivers/virtio_net.zig enumerate PCI and then return NotImplemented for every operation. boot/uefi.zig has an efi_main nothing calls. The VGA console has no scroll. clock_gettime returns a placeholder (TSC TODO).
The PL011 is polled while the keyboard is interrupt-driven.
Its receive INTID is in the device tree and nothing reads it. Has not bitten (16-byte FIFO, humans type slower), which is the kind of true statement that stops being true without warning.
The kernel calls itself ClarityOS in every marker.
REBRAND.md renamed the OS to KyanOS. Both gates and all three Python tools grep the old name, so the rename has reach. Owner's decision; recorded, not acted on.
clarity desktop crashes instead of explaining.
Launching KyanOS — close the window to exit.
error: Failed to open library "libSDL2-2.0.so.0" ... ERR_DLOPEN_FAILED
host_supported() checks the platform, not whether SDL2 is present, so on a machine without it the friendly message never prints and a Bun stack trace does. Small fix, high first-impression cost.

Low

  • 26 public kernel functions have no reference anywhere (list under Dead code). Some are API surface (port.in16), some are dead by design (tty.set_mode), one is a hazard: vmm.handle_page_fault exists and is never wired.
  • kernel/README.md and RUNNING.md carry 34 and 46 em dashes; ROADMAP_OS.md 72. House style avoids them.
  • ITARGETSR in gic.zig is written and, on QEMU's uniprocessor GIC, has no observable effect; the comment now says so. It will matter on a multi-core GIC.
Section 3

What is strong

  • The aarch64 kernel is verified the way kernels should be. Address spaces are checked by asking the MMU, not by reading a bit back. PAN is enabled and the gate runs a CPU without PAN too, because on that one doing it wrong also works. User pointers are translated for the access being made; the init program passes a pointer into its own text to prove read refuses it.
  • Negative testing is a habit, not a slogan. Every increment this month broke the thing on purpose and required a distinct failure: the keyboard interrupt (11 of 46 characters without it), the syscall unmask (same), the serial receive (0 key presses without it). A negative test that passed was treated as a broken test, found the cause, and was written up.
  • The gate reads pixels and types. fb_check replays the console's own wrapping over the serial log and compares every cell to a glyph it renders itself. key_check sends over two hundred virtqueue events through a queue of sixty-four to prove buffers recycle. serial_check attaches no keyboard and fails if it finds one.
  • One C program runs on both architectures with identical bytes. kernel/user/libc (strtod, dtoa, printf, malloc, setjmp, math) is small, shared, and pinned by a literal float line the gate requires on both.
  • Failures are diagnosed, not retried. A three-second timeout that made the OS unusable by hand became a kernel command line rather than a bigger number. A write-only UART became a serial console rather than a workaround.
  • The browser desktop is real. web/ compiles the Clarity compositor, window manager and apps to JavaScript and paints them on a canvas with mouse routing. It is the one demoable OS surface today, and it is live (if stale).
Section 4

What is holding us back

  1. Two OS stories in one tree. The kernel gate proves a Zig init and a compiled Clarity program. The README, os_build, init_app, display_server and the QuickJS runtime describe a different OS whose init spawns /bin/clarity-compositor and friends, binaries nothing builds. Until one story is chosen, every doc drifts and every reader is misled somewhere.
  2. No process table. Everything a person expects from a shell (start a program, list a directory, wait, come back) is downstream of this one piece.
  3. The x86 side has no user-memory layer. The aarch64 port did it properly; the x86 kernel still trusts every pointer. Every new syscall on x86 inherits the hole.
  4. The OS userspace has never had a real boundary to meet. Its tests pass against stubs. As the kernel grows syscalls, the simulations should become contract tests against the real thing, or go.
  5. Apple hardware is the goal and GICv2 is the ceiling. No native speed on a Mac until GICv3, and no bare metal until AIC and m1n1.

Section 6

Code challenged

Places where the code is doing something worth arguing with, mine included.

  • sys_write falls back to the console on EBADF for fd 1 and 2. It makes early bring-up easier and it means a program can never learn that stdout is not open. The fallback should go when a process table gives every process real descriptors.
  • The page-fault handler halts the machine. Correct for a kernel with no demand paging, but it means a user program's bad pointer takes down everything, on x86 today and on aarch64 only because pointers are translated first. A fault in user mode should kill the process, not the kernel.
  • syscall_depth as a preemption guard. It is 0 or 1 and correct, but it encodes "we do not know how to suspend a syscall" as policy. It should be replaced, not extended, when the scheduler lands.
  • One line editor for every reader. drivers/stdin.zig keeps a single editor so the boot selftest and read(2) do not split keystrokes. That is right today and wrong the moment two processes read.
  • Timeouts standing in for blocking. clarity.idle= made it configurable; it is still a spin. The kernel command line was the right fix for the person; the scheduler is the fix for the design.
  • gic.init cycles the distributor. Adding a second interrupt needed gic.enable precisely because init turns everything off and on. Fine now; on hardware where the timer is already running that pattern is a missed tick.
  • Markers are the contract, and they are prose. The gate greps sentences like "[ok] keyboard: interrupt .* routed to this core". Every wording change is a CI change. A short stable tag per marker ([ok:kbd-irq]) would let the prose improve without touching the gate.
  • The line-count claims in the README are off by 4x for the kernel. "~3,600-line Zig micro-kernel" was true in July; the tree has 13,502 lines of Zig and assembly. Numbers in prose rot; the index generator now computes them.

Section 8

Not gaps, but assets for the goal

  • The shared C runtime path. A Clarity program compiles to C, links against a 1,000-line libc, and runs on both kernels with identical output. This is the userspace strategy that works; the roadmap should say it is the only one.
  • The device-tree parser. Written for QEMU's virt, but m1n1 hands Apple hardware the same format. It is the first piece of the bare-metal path that already exists.
  • The renderer and compositor are real and tested. Per-window framebuffers, dirty rects, z-order, hit testing, drag and snap, and now the Kyan identity. They are ready for a real display target; what they lack is one.
  • The test tooling is reusable. key_check, serial_check and fb_check are the harness a future ls, exec or GICv3 lands into. New features arrive with a way to fail.
  • Both architectures share the filesystem unchanged. fs/vfs.zig and fs/tmpfs.zig crossed over with zero edits, which says the shared layer is actually shared.
Section 9

What needs doing, in order

  1. Choose the one OS story and make the README, os_build and init_app tell it. Retire the QuickJS runtime from the pipeline; make clarity os build produce the ISO the gate boots.
  2. User-memory layer on x86_64: translate-for-read and translate-for-write, SMAP, and EFAULT instead of a kernel fault. Port the aarch64 tests.
  3. A process table and scheduler on aarch64, then exec, getdents, and blocking read. This unlocks ls, running programs from the shell, and preemption inside system calls.
  4. Wire what exists and is not called: per-process descriptor tables, orphan reparenting, a page-fault handler that kills a process instead of the machine.
  5. GICv3 driver, then -accel hvf on the M5. Then the launcher picks the aarch64 kernel on arm64 hosts.
  6. Rebuild the browser desktop in the Pages workflow and stop tracking the bundle. Decide the fate of the spring identity and the kernel simulations.
  7. Rename the markers to KyanOS once, with stable tags, and update both gates and the three tools in the same change.
  8. m1n1 and AIC: the bare-metal track, after everything above.
